# PayOps Implementation Plan

> Execute tasks inline in the current workspace, using test-first implementation and fresh verification.

**Goal:** Deliver the local payment reliability and DevOps lab in the supplied proposal.

**Architecture:** A shared Python image provides four processes. PostgreSQL owns state, leases, history, and scheduled outbox rows; RabbitMQ delivers confirmed durable work. Compose and kind use the same application and operations CLI.

**Tech stack:** FastAPI, SQLAlchemy, psycopg, Pika, pytest, Docker, kind, Jenkins, Prometheus, Grafana, Alertmanager, Loki, Alloy, Locust, Terraform.

**Spec:** `docs/superpowers/specs/2026-10-31-payops-design.md`

## Global constraints

- Local-only simulated payments; no paid or cloud resources.
- No committed secret values; persistent database/broker volumes.
- Bounded retries; at-least-once delivery; duplicate-safe provider calls.
- Windows Python CLI and Linux/WSL Make entry points.

## Review focus

- Simultaneous idempotency requests and different-payload reuse.
- Crash after provider success and before worker commit.
- Crash after broker confirmation and before outbox commit.
- Worker loss on the last attempt and stale worker completion.
- Failed rollout restoration, missing prerequisites, and persistent storage boundaries.
