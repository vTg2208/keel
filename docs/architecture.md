# Architecture and reliability guarantees

`payops/api.py` validates synthetic requests and calls `domain.create_payment`. Payments, the first history event, and the first outbox event commit together. The unique database constraint on `idempotency_key` serializes concurrent submissions; the stored normalized request digest detects conflicting reuses. The API can accept work during a broker outage because the queue is downstream of PostgreSQL.

`payops/publisher.py` locks unpublished due outbox rows with `FOR UPDATE SKIP LOCKED`, sends persistent RabbitMQ messages with mandatory routing and publisher confirms, and then commits `published_at`. Confirmed publish followed by process/transaction failure can publish the same event again. The design therefore provides at-least-once delivery, not exactly-once transport. Publisher confirms and consumer acknowledgements serve separate roles; see [RabbitMQ acknowledgements and confirms](https://www.rabbitmq.com/docs/confirms).

`payops/worker.py` acknowledges only after the database records the result and any retry/dead-letter event. A row lock claims a payment, increments its attempt count, and generates a lease token. It releases the transaction before the HTTP call. Terminal states and active claims absorb duplicate messages. A completion must match the current token. The publisher recovers expired processing leases and schedules another durable event; a stale process cannot overwrite a newer attempt. The provider timeout is shorter than the lease. A worker stuck while its metrics server remains reachable is detected by its heartbeat.

Retries use PostgreSQL `available_at` rather than sleeping while holding an unacknowledged work item. Default maximum is three total attempts; default delays after attempts one and two are two and four seconds. Transient errors and malformed responses retry; business declines finish immediately. Exhaustion commits a `failed` state and outbox row routed to `payops.dead`. Malformed broker messages are rejected into the dead-letter exchange. Quorum queues use a delivery limit as a second bound on infrastructure redelivery. See [quorum queue reliability](https://www.rabbitmq.com/docs/quorum-queues).

The simulator stores successful/declined decisions separately in `provider_results`, keyed by payment ID. Every attempt uses the same payment ID, amount, currency, and scenario. On a retry after response loss, it returns the original reference. The `timeout_after_success` scenario deliberately commits before delaying the first response. This models idempotent provider behavior without transferring money. A real provider would need an explicit, verified idempotency/reconciliation contract.

If the final attempt is lost before recording its response, lease recovery marks the payment `unknown`, records a `reconciliation_required` history event, and sends a dead letter. It does not declare the provider charge failed, invent a successful result, or exceed the attempt bound. Inspect provider state and reconcile manually in that exercise. No distributed transaction can atomically combine an external charge, PostgreSQL commit, and RabbitMQ acknowledgement.

All service credentials are generated locally and supplied through environment variables or Kubernetes Secrets. Simulator and payment tables share one PostgreSQL server for a compact lab; their transaction boundaries are independent. Worker/publisher telemetry counters describe process activity; PostgreSQL-backed status gauges describe durable totals. Loki uses local filesystem retention and Alloy collects logs through Docker or the Kubernetes pod-log API. See [Alloy Docker log source](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.docker/).

v1 schema initialization uses SQLAlchemy `create_all`, called explicitly by a migration container/job. It never drops tables and is not a general migration engine. Application rollback requires schema compatibility. Future schema evolution needs tracked migration versions and expand/contract rollout practices.

On Docker's containerd image store, kind can reject multi-platform image exports when other architectures are absent locally. The deployment CLI detects Docker's platform-export capability and uses a temporary archive containing only the node platform, following [kind's documented workaround](https://kind.sigs.k8s.io/docs/user/known-issues/#unable-to-kind-load-docker-images). It cleans up the archive afterward and keeps Docker's global settings unchanged. Older classic-store Docker clients use standard kind image loading. Jenkins includes Docker CLI 28 for the platform-aware export.
